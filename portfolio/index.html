Anomaly Agent

A spreadsheet watcher. It notices when a business metric leaves its normal range, explains the move in plain English, and emails someone before the manager has to find it.

The problem

Managers don't want to open a spreadsheet every morning to see whether something broke. A notebook full of charts shows that you can inspect data; it doesn't tell anyone when revenue falls off a cliff on a Tuesday. This project turns a spreadsheet into something that watches itself.

What it does

Write rulesin plain English, one per line
Reviewa readback of what each rule really does, plus how often it would have fired
Detectmoves outside the recent normal range
Explain & alerta short summary by email, no repeat spam

Rules anyone can edit

Rules are sentences, not config. Each is compiled into a validated rule and read back before anything runs. Sentences the built-in patterns can't parse can go to Claude, whose output passes through the same validation and the same confirmation step.

What an anomaly is

A value that is unlikely given what that metric normally does. Each metric is compared with a baseline built from the previous 28 days only, so a spike can't hide itself by raising its own baseline. The default score uses the median and median absolute deviation, which a past spike barely moves. Moves under 5% are ignored even if statistically odd, and flat series produce no score rather than an infinite one. Combined patterns (revenue up while conversion falls) catch problems a single metric would miss.

How I tested it

  • Ground truth. The generator plants five anomalies (traffic-quality shift, refund surge, traffic collapse, ad-spend spike, checkout failure) and records them, so recall and false alarms are measured, not eyeballed. The committed sample file: 5/5 caught, 3 false-alarm days.
  • Many datasets, not one. A single file can flatter a detector, so the benchmark runs 20 noise seeds. Rules were tuned on seeds 0-19 and scored on 200-219.
  • It got better for measurable reasons. The first draft (14-day baselines, one classic z-score) fired on 3.0% of normal days. 28-day baselines with median/MAD cut that to about half with recall unchanged. A 13% cost move was paging people as critical, so cost became a two-tier rule. Both changes are in the README with the numbers.
  • 59 automated tests covering the sentence parser, rule validation, detectors, data-quality checks, de-duplication, the CLI's confirmation gate and the Streamlit app.

Decisions worth explaining

  • Templates first, Claude second. Deterministic parsing is free, offline and reproducible. Claude handles only what templates can't, and a human confirms its interpretation before anything runs, because a silently misread alert rule is worse than none.
  • Only column names and rule sentences ever reach the model, never spreadsheet values. Names are reduced to [a-z0-9_] and length-capped, which also blunts prompt injection through a malicious header.
  • Bad input is reported as bad input. Gaps, duplicate dates, unreadable cells and stale files raise data-quality notices instead of fake anomalies.
  • Repeat alerts are suppressed for a cooldown window, and re-running the same data is idempotent. Alert fatigue kills monitoring tools faster than missed alerts.

Limitations

  • All results are on synthetic data I generated. Real data has seasonality, promotions and outliers this generator does not.
  • The five planted anomalies sit on the same dates in every simulated dataset; only the noise changes. The benchmark shows robustness to noise, not to every anomaly shape.
  • The live Claude integration is tested against a fake client (validation and guard logic), not yet against the real API.
  • No seasonality model; a large, predictable weekend swing can trigger alerts. A per-weekday baseline is the next step.
